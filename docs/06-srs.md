# Технічне завдання та Специфікація вимог (SRS)
**Проєкт:** Інтернет-магазин одягу «TrendWave»  
**Версія:** 1.0 | **Дата:** 19.11.2026

---

## Частина I. Технічне завдання (ТЗ)

### 1. Загальні відомості
* **Повна назва системи:** Вебзастосунок електронної комерції «Інтернет-магазин одягу "TrendWave"».
* **Замовник і виконавець:** Замовник — викладач дисципліни (навчальний заклад); виконавець — студент групи КН-4 Карпишин Роман.
* **Підстава для розроблення:** Індивідуальне навчальне завдання з дисципліни «Проєктування програмного забезпечення».
* **Строки виконання:** 02.11.2026 — 20.12.2026 (7 тижнів).

### 2. Призначення і цілі
* **Призначення:** Автоматизація онлайн-продажу одягу, підбору розмірів за параметрами тіла та обліку складських залишків.
* **Цілі створення:** Зменшення кількості повернень одягу через невідповідність розміру, прискорення оформлення замовлення до 3 хвилин, автоматизація контролю залишків за комбінацією «колір + розмір».
* **Цільова аудиторія:** Покупці (гості та зареєстровані користувачі), менеджер магазину (контент і замовлення), адміністратор системи.

### 3. Опис предметної області
* **Основні поняття:** Товар (модель одягу), Варіація товару (колір + розмір + залишок), Таблиця лекал (заміри моделі), Кошик, Замовлення, ТТН.
* **Ключові процеси:** Пошук і фільтрація каталогу → підбір розміру за антропометричними даними → формування кошика й оформлення замовлення → підтвердження, списання залишків та відправка менеджером.
* **Обмеження:** Неможливість замовлення товару з нульовим залишком; підтримка лише гривневих розрахунків (UAH); робота виключно через веббраузер без нативних мобільних клієнтів.

### 4. Вимоги до системи
* **Функціональні вимоги (FR-01 — FR-15):** Реєстрація/вхід, каталог із фільтрами, інтелектуальний підбір розміру, кошик, оформлення та відстеження замовлень, відгуки, адмін-панель для керування товарами, залишками, замовленнями та ролями.
* **Нефункціональні вимоги (NFR-01 — NFR-08):** Завантаження сторінок ≤ 1,5 с; до 200 одночасних користувачів; хешування паролів (bcrypt/Argon2id); HTTPS (TLS 1.2/1.3); оформлення замовлення ≤ 4 кроки; адаптивність 360–1920 px; Uptime ≥ 99,5%.
* **Вимоги до інтерфейсів, даних і середовища:** Адаптивний вебінтерфейс (HTML5/CSS3/JS); реляційна БД (PostgreSQL / MySQL) зі щоденним резервним копіюванням; розгортання у хмарному середовищі Linux.

### 5. Вимоги до документації

* **Тестування:** Перевірка функціональності за сценаріями *Given-When-Then* (критеріями приймання SRS) та перевірка NFR інструментами Lighthouse й OWASP ZAP.
* **Критерії приймання:** Реалізація 100% вимог категорії *Must have* (MVP), відсутність критичних помилок (HTTP 5xx), наявність повного комплекту документів у репозиторії.

## Частина II. Специфікація вимог до програмного забезпечення (SRS)

### 1. Вступ
* **1.1 Призначення документа:** Цей документ визначає повний набір функціональних і нефункціональних вимог до MVP та подальших версій інтернет-магазину одягу «TrendWave» (версія 1.0) для розробників, тестувальників і замовника.
* **1.2 Межі продукту:** «TrendWave» — вебплатформа електронної комерції для продажу одягу з інтелектуальним підбором розміру за параметрами фігури та обліком складських залишків. Система не включає власний платіжний шлюз (використовується інтеграція зовнішнього еквайрингу) та нативні мобільні застосунки.
* **1.3 Посилання:** ISO/IEC/IEEE 29148:2018; Картка проєкту (`docs/01-project-card.md`); Каталог вимог (`docs/05-requirements.md`).

### 2. Загальний опис
* **2.1 Перспектива продукту:** «TrendWave» є самостійною клієнт-серверною вебсистемою (SPA/SSR фронтенд + REST API бекенд + реляційна БД) із підключенням зовнішніх API служб доставки (Нова Пошта) та онлайн-оплати.
* **2.2 Класи користувачів:**
  * *Гість* — перегляд каталогу, підбір розміру, кошик, оформлення замовлення без реєстрації.
  * *Покупець* — функції гостя + збереження замірів тіла, історія замовлень, список обраного, відгуки.
  * *Менеджер* — керування товарами, залишками за розмірами, зміна статусів замовлень, внесення ТТН.
  * *Адміністратор* — повний доступ + керування ролями та блокування облікових записів.
* **2.3 Середовище функціонування:** Актуальні версії браузерів Chrome, Firefox, Safari, Edge на ПК та смартфонах (ширина екрана 360–1920 px); серверна частина — Linux-контейнер із підтримкою HTTPS (TLS 1.2/1.3).
* **2.4 Припущення та залежності:** Користувачі мають стабільний доступ до Інтернету; коректність роботи підбору розмірів залежить від точного заповнення менеджером таблиці лекал для кожної моделі одягу.

### 4. Додатки до SRS

#### Додаток А. Глосарій термінів
* **Варіація товару (SKU)** — конкретна комбінація моделі одягу, кольору та розміру, що має власний складський залишок.
* **Крій (Fit)** — особливість посадки моделі одягу на фігурі (наприклад, *Slim Fit* — приталений, *Regular* — стандартний, *Oversize* — вільний), що враховується алгоритмом підбору розміру.
* **Таблиця лекал** — набір еталонних замірів конкретного виробу (довжина виробу, напівобхват грудей, талії, стегон у сантиметрах) для кожного розміру.
* **MVP (Minimum Viable Product)** — мінімально життєздатний продукт, що містить лише критично необхідний функціонал (категорія *Must have*) для запуску та перевірки цінності.
* **ТТН (Товарно-транспортна накладна)** — унікальний 14-значний трек-номер поштового відправлення для відстеження доставки замовлення.

## Частина IV. Індивідуальне завдання: Процес керування змінами вимог

### 1. Регламент керування змінами у проєкті «TrendWave»
Оскільки базову версію SRS (v1.0) затверджено, будь-які подальші зміни вимог проходять формалізовану процедуру:

1. **Ініціювання запиту (Подача CR):** Запит на зміну (*Change Request — CR*) може подати замовник (викладач), менеджер магазину або розробник шляхом створення Issue на GitHub із міткою `change-request` та заповненням шаблону (суть зміни, обґрунтування, пріоритет).
2. **Аналіз впливу (Impact Analysis):** Виконавець (розробник) оцінює вплив запропонованої зміни на:
   * пов'язані вимоги (через матрицю трасування);
   * архітектуру системи та схему бази даних;
   * трудомісткість і календарний план (чи не зірве зміна дедлайн MVP).
3. **Прийняття рішення (Затвердження):** Рішення про прийняття, відхилення або перенесення зміни у наступний реліз (*Could/Won't have*) приймає замовник (керівник проєкту) на основі результатів аналізу впливу.
4. **Оновлення документації та трасування:** У разі затвердження CR розробник оновлює відповідні пункти у `docs/06-srs.md`, коригує матрицю трасування, підвищує мінорну версію документа (наприклад, з `1.0` до `1.1`), фіксує запис у **Журналі змін** і створює нову картку завдання на Kanban-дошці.
